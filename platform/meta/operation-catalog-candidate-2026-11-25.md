# Operation catalog candidate

This source-only backport starts at `53e3ee2e25455fb8a16cf2cd7c93f0990f73d5f6`, the API source verified against the active `52b7eed8-b5c0-4e4c-b72a-41acda73ffb2` build on November 25, 2026. It has not been uploaded or activated.

It adds authenticated `POST /app-billing/projects.capabilities` discovery, using the existing connected-app ownership and preview checks. The catalog uses the pinned Cloudflare CLI `1.0.0-rc.2` snapshot, schema `1.0`, SHA-256 `d399ac23573b5ac40f0ae7ad1752a5be036429e239de176af85cde4693498f2d`. The snapshot contains 2,947 operation summaries. These summaries do not grant execution access or describe complete input validation.

The existing resource inventory still describes database, file, key-value and queue actions. A separate schema-backed operation registry now exposes file reads and conditional text saves through the same provider helpers. Other resource types return an explicit unavailable reason from this new registry; this does not remove their existing actions. External database connections remain unsupported executable resources on this branch. There are no Hyperdrive inspection changes, SQL changes, migrations, new bindings or dependency upgrades.

`POST /app-billing/projects.resourceOperations` accepts `{project, owner, resourceId}`. Its `data` includes `appId`, `resourceId`, `checkedAt`, `available`, nullable `reason`, `coverage: "registered-operations"`, and `operations`. Each operation has `id`, a SHA-256 `version`, `effect`, `title`, `description`, `inputSchema`, `outputSchema`, and an `errors` array of `{code, status, message}`. Schemas come from the validators used by the Realtime registry. The save text field also declares `x-maxUtf8Bytes: 65536`, enforced before storage access.

`POST /app-billing/resources.invoke` accepts that scope plus `{operation, version, expectedEffect, input}`. A write also requires `confirmation: "reviewed"` from the connected application's reviewed-action path. That marker is not a separate user credential: the application remains responsible for authenticating its user and reviewing the exact input. The API independently checks its connected-client ownership, operation availability, current version, effect, input schema and resource mapping. It rejects writes submitted as read sources. It does not accept caller-selected provider URLs or account identifiers.

The first operations are `files.readText` with `{key}` and `files.saveText` with `{key, text, expectedEtag}`. Responses keep the existing `{data: {appId, resourceId, action, kind, ...}}` shape. The registry validates the output schema, rechecks access after reads, and preserves conditional writes, conflict outcomes and unknown write outcomes. Input and authorization failures return HTTP errors before execution. Operation descriptors can be saved as references by ID/version; clients must rediscover stale versions and fetch current data when reopening a view.

Before any upload, verify the active API source and binding configuration again. An upload would change the shared Platform API; testing a connected application's dev environment does not make that API a separate development installation.

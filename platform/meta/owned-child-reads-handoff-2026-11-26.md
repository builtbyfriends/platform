# Owned child reads — DED-580 checkpoint

## Implemented, not deployed

The shared schema-backed read adapter now supports a selected child under an owned parent. Two installed policies use it: Queue consumer details (`queues-get-consumer`) and R2 custom domain configuration (`r2-get-custom-domain-settings`). They use the existing invocation route and generated-view capability model, with input `{ child: <selected collection identity> }`. No new grants, account selectors, provider URLs, writes or product-specific renderer were added.

The adapter injects the account and parent from the authorized resource record. It validates the child against the exact parameter schema and a bounded policy. It checks the complete owned collection before and after the detail fetch; an absent, duplicate or removed child causes failure. The detail identity must equal the selection. Each request retains the existing pre/post ownership checks. The three reads share an eight-second deadline. Missing collection schema makes the child capability unavailable, rather than bypassing membership proof. Output is projected: worker names, zone IDs and provider credentials stay private. R2 cipher settings are bounded structured data.

The detail descriptor includes its parent descriptor version, so changing the membership policy invalidates old child views. Existing policies retain their descriptor construction and tested version hashes. These policies currently require complete collections of at most 200 entries; paginated or unknown-completeness collections are not accepted as membership proof.

Files: `cloudflare-provider-read.ts`, `resource-operations.ts`, child unit tests, existing provider unit/route tests, and two immutable OpenAPI fixtures. The source branch is `codex/owned-child-details`, based on `9c48d6bb`, in the isolated `platform-owned-child-details` worktree. No shared checkout or traffic was changed.

## Next ownership/discovery change — not implemented

The current root boundary is still the seven-type `resources` table model in `schema.ts`, its product map in `app-runtime-catalog.ts`, `getProjectResources`, and `ownedResourceCaller`. An arbitrary OpenAPI product or a model-supplied ID is not a project resource. Adding enum members alone would not establish ownership.

Introduce a server-owned resource-reference union shared by inventory, catalog and invocation. Keep today's provisioned-resource reference, and add references backed by existing authoritative project records. Each reference needs a stable opaque public ID, project/installation scope, product/family, a server-only provider locator, proof kind/source ID/source generation and a fresh revalidation method. The resolver must compare the same proof generation before and after calls; absence, reconciling state, revocation or ambiguous matches must withhold execution. The model can select an opaque reference but cannot construct proof or supply the underlying provider locator. Discovery remains independent from execution policy.

The smallest next new-family proof already exists for Cloudflare Access applications: `project_zero_trust` stores project-owned protected/bypass application IDs, names, reconciliation operation and updated time. `zero-trust/project.ts` provisions them and `zero-trust/state.ts` exposes safe project status. A read-only inventory resolver could expose ready, reconciled applications as generic Resource nodes, keep their provider handles private, and recheck the exact row, ownership, operation and application identity. Access configuration reads would still need an installed, schema-pinned projection policy; do not expose raw policies, audiences or authentication internals by default. This can prove a new family without a dashboard type branch or account-wide listing. Test foreign project selection, changed application ID, reconciling/error state, changed reconciliation generation, missing record and late revocation.

Containers need separate work: the `container` resource type includes historical handles, while managed deployment manifests plus dispatch namespace bindings provide the stronger proof. Existing `operator/sandbox-operations.ts:verifyApplication` compares manifest identity and the application's Durable Object namespace. It must not be reused as an account-wide operator grant. Extract a bounded project-scoped resolver only after establishing its live manifest contract; do not treat a string ID or name match as proof.

Suggested integration points: add the resource-reference resolver beside `app-runtime-resource-owner.ts`; inventory uses it alongside `db/resources.ts`; catalog product selection uses its family; invocation builds the same authorized caller from the resolved reference. Crowded's reconciliation already keeps unknown inventory kinds as generic Resource nodes, so feed it the opaque ID and safe label rather than introducing another product-specific frontend switch. Continue to keep observed deployment connections separate from ownership-only resource inventory.
